# Constructors, Destructors, and RAII Interview Questions

This topic focuses on C++ object lifetime. Interviewers often use constructors, destructors, and RAII questions to check whether a candidate can write exception-safe code, manage resources correctly, and reason about initialization order.

## 1. What is a constructor?

**Short answer:** A constructor is a special member function that initializes an object when it is created.

**Detailed answer:**
A constructor has the same name as the class and no return type. It establishes the initial valid state of an object. Constructors can be default, parameterized, copy, move, explicit, delegating, or inherited depending on the class design.

**Example:**

```cpp
#include <string>
#include <utility>

class User {
public:
    User(std::string name, int age)
        : name_(std::move(name)), age_(age) {}

private:
    std::string name_;
    int age_;
};
```

The member initializer list initializes `name_` and `age_` before the constructor body runs.

**Interview point:** A constructor should leave the object in a valid state or fail by throwing an exception.

**Common mistake:** Doing all initialization inside the constructor body instead of using the member initializer list.

---

## 2. What is a destructor?

**Short answer:** A destructor is a special member function that runs when an object is destroyed.

**Detailed answer:**
A destructor releases resources owned by the object, such as memory, file handles, locks, sockets, or other system resources. It has the same name as the class preceded by `~` and has no return type or parameters.

**Example:**

```cpp
#include <cstdio>

class FileHandle {
public:
    explicit FileHandle(const char* path) {
        file_ = std::fopen(path, "r");
    }

    ~FileHandle() {
        if (file_) {
            std::fclose(file_);
        }
    }

private:
    FILE* file_ = nullptr;
};
```

**Interview point:** Destructors should generally not throw exceptions. Throwing during stack unwinding can terminate the program.

**Common mistake:** Thinking destructors are only for memory cleanup. They are for any resource cleanup.

---

## 3. What is the member initializer list, and why is it important?

**Short answer:** The member initializer list initializes members before the constructor body executes.

**Detailed answer:**
Members are initialized before the constructor body runs. If you assign inside the constructor body, the member may first be default-initialized and then assigned, which can be inefficient or impossible for `const` members, references, or types without default constructors.

**Example:**

```cpp
#include <string>

class Employee {
public:
    Employee(std::string name, int id)
        : name_(std::move(name)), id_(id), displayName_(name_) {}

private:
    std::string name_;
    const int id_;
    std::string displayName_;
};
```

**Important rule:** Members are initialized in the order they are declared in the class, not the order listed in the initializer list.

```cpp
class Example {
public:
    Example() : b_(1), a_(b_) {}

private:
    int a_;
    int b_;
};
```

Here, `a_` is initialized before `b_` because `a_` is declared first. This can cause bugs.

**Common mistake:** Believing initializer list order controls initialization order. Declaration order controls it.

---

## 4. What is a default constructor?

**Short answer:** A default constructor is a constructor that can be called with no arguments.

**Detailed answer:**
A default constructor may be implicitly generated by the compiler or explicitly declared by the programmer. It is used when objects are default-initialized, value-initialized, placed in containers, or created as array elements.

**Example:**

```cpp
class Point {
public:
    Point() : x_(0), y_(0) {}

private:
    int x_;
    int y_;
};
```

**Modern C++ defaulting:**

```cpp
class Config {
public:
    Config() = default;
};
```

**Interview point:** If you declare some constructors, the compiler may not generate a default constructor automatically.

**Common mistake:** Assuming every class always has a default constructor.

---

## 5. What is an explicit constructor?

**Short answer:** An `explicit` constructor prevents unintended implicit conversions.

**Detailed answer:**
A constructor with one argument can be used by the compiler for implicit conversion unless it is marked `explicit`. This can create surprising behavior in function calls and assignments.

**Example without `explicit`:**

```cpp
class UserId {
public:
    UserId(int value) : value_(value) {}

private:
    int value_;
};

void loadUser(UserId id) {}

loadUser(42); // allowed due to implicit conversion
```

**Better:**

```cpp
class UserId {
public:
    explicit UserId(int value) : value_(value) {}

private:
    int value_;
};

loadUser(UserId{42}); // clear and intentional
```

**Interview point:** Mark single-argument constructors `explicit` unless implicit conversion is intentionally part of the type design.

---

## 6. What is constructor delegation?

**Short answer:** Constructor delegation allows one constructor to call another constructor of the same class.

**Detailed answer:**
Delegating constructors reduce duplication and help keep initialization logic consistent. The delegated-to constructor runs first, then the body of the delegating constructor runs.

**Example:**

```cpp
#include <string>

class Connection {
public:
    Connection() : Connection("localhost", 8080) {}

    Connection(std::string host, int port)
        : host_(std::move(host)), port_(port) {}

private:
    std::string host_;
    int port_;
};
```

**Common mistake:** Trying to call another constructor like a normal function inside the constructor body.

```cpp
Connection() {
    Connection("localhost", 8080); // creates a temporary, does not initialize this object
}
```

## 7. What is RAII, and why does it improve exception safety?

**Short answer:** RAII binds resource lifetime to object lifetime, so destructors release resources automatically even when exceptions occur.

**Detailed answer:**
Without RAII, code must manually release resources on every path, including error paths. RAII makes cleanup deterministic: when the object leaves scope, its destructor runs.

**Bad example:**

```cpp
void process() {
    int* data = new int[100];
    riskyOperation();
    delete[] data;
}
```

If `riskyOperation()` throws, `delete[] data` is skipped.

**Better:**

```cpp
#include <vector>

void process() {
    std::vector<int> data(100);
    riskyOperation();
}
```

The vector cleans itself up during stack unwinding.

**Common mistake:** Adding manual cleanup everywhere instead of using RAII types.

---

## 8. What is stack unwinding?

**Short answer:** Stack unwinding is the process of destroying local objects as control leaves scopes during exception handling.

**Detailed answer:**
When an exception is thrown, C++ exits scopes until it finds a matching handler. During this process, destructors for fully constructed local objects are called in reverse order of construction.

**Example:**

```cpp
#include <iostream>

class Trace {
public:
    explicit Trace(const char* name) : name_(name) {
        std::cout << "construct " << name_ << '\n';
    }

    ~Trace() {
        std::cout << "destroy " << name_ << '\n';
    }

private:
    const char* name_;
};

void f() {
    Trace a("a");
    Trace b("b");
    throw std::runtime_error("error");
}
```

`b` is destroyed before `a` during stack unwinding.

**Interview point:** RAII depends on stack unwinding to provide automatic cleanup during exceptions.

## 9. What happens if a constructor throws an exception?

**Short answer:** The object is not considered fully constructed, so its destructor is not called, but destructors for already constructed members and base classes are called.

**Detailed answer:**
If construction fails, C++ cleans up the parts that were successfully constructed. The destructor for the object itself does not run because the object never became complete.

**Example:**

```cpp
class Resource {
public:
    Resource();
    ~Resource();
};

class Widget {
public:
    Widget() : resource_() {
        throw std::runtime_error("failed");
    }

    ~Widget() {
        // not called if constructor throws
    }

private:
    Resource resource_;
};
```

`Resource::~Resource()` is called, but `Widget::~Widget()` is not.

**Design implication:** Use RAII members so partially constructed objects clean up correctly.

**Common mistake:** Relying on the class destructor to clean up resources acquired manually before the constructor throws.

## 10. What is the order of construction and destruction in inheritance?

**Short answer:** Base classes are constructed before derived classes, and destruction happens in the reverse order.

**Detailed answer:**
When creating a derived object, C++ first constructs base class subobjects, then data members, then runs the derived constructor body. During destruction, the derived destructor body runs first, then members are destroyed, then base class destructors run.

**Example:**

```cpp
#include <iostream>

class Base {
public:
    Base() { std::cout << "Base constructed\n"; }
    ~Base() { std::cout << "Base destroyed\n"; }
};

class Derived : public Base {
public:
    Derived() { std::cout << "Derived constructed\n"; }
    ~Derived() { std::cout << "Derived destroyed\n"; }
};
```

Output order on construction:

```text
Base constructed
Derived constructed
```

Output order on destruction:

```text
Derived destroyed
Base destroyed
```

**Interview point:** Avoid calling virtual functions from constructors or destructors expecting derived behavior. During base construction/destruction, the dynamic type is treated as the current class level.

**Common mistake:** Expecting a base constructor to call an overridden derived method.

---

## 11. What are special member functions in C++?

**Short answer:** Special member functions are functions the compiler may generate automatically to manage object creation, copying, moving, and destruction.

**Detailed answer:**
The main special member functions are the default constructor, destructor, copy constructor, copy assignment operator, move constructor, and move assignment operator. They define how objects are created, copied, moved, assigned, and destroyed.

**Example:**

```cpp
class Buffer {
public:
    Buffer();
    ~Buffer();
    Buffer(const Buffer& other);
    Buffer& operator=(const Buffer& other);
    Buffer(Buffer&& other) noexcept;
    Buffer& operator=(Buffer&& other) noexcept;
};
```

**Interview point:** Declaring one special member function can affect whether others are implicitly generated. This is why the Rule of Three, Rule of Five, and Rule of Zero matter.

**Common mistake:** Adding a destructor for manual cleanup but forgetting that copy operations may now need custom behavior too.

## 12. Why should constructor initializer lists match member declaration order?

**Short answer:** Members are initialized in declaration order, so writing the initializer list in the same order prevents misleading code and subtle bugs.

**Detailed answer:**
The order in the initializer list does not control initialization order. The class member declaration order does. If one member depends on another, the depended-on member must be declared first.

**Bad example:**

```cpp
class Session {
public:
    Session() : token_(createToken(userId_)), userId_(42) {}

private:
    std::string token_;
    int userId_;
};
```

Here, `token_` is initialized before `userId_` because `token_` is declared first. The initializer list visually suggests the opposite dependency.

**Better:**

```cpp
class Session {
public:
    Session() : userId_(42), token_(createToken(userId_)) {}

private:
    int userId_;
    std::string token_;
};
```

**Interview point:** Many compilers warn about mismatched initialization order. Treat those warnings seriously.

## 13. Why is calling virtual functions from constructors or destructors dangerous?

**Short answer:** Virtual calls inside constructors or destructors do not dispatch to more-derived classes the way many people expect.

**Detailed answer:**
During base class construction, the derived part of the object has not been constructed yet. During base class destruction, the derived part has already been destroyed. For that reason, virtual calls resolve to the current class level, not to a more-derived override.

**Example:**

```cpp
#include <iostream>

class Base {
public:
    Base() {
        setup();
    }

    virtual ~Base() = default;

    virtual void setup() {
        std::cout << "Base setup\n";
    }
};

class Derived : public Base {
public:
    void setup() override {
        std::cout << "Derived setup\n";
    }
};
```

Constructing `Derived` calls `Base::setup()` from the `Base` constructor.

**Common fix:** Use a separate initialization function after construction, or redesign so base constructors do not depend on derived behavior.

**Common mistake:** Assuming `virtual` always means the most-derived override is called.

## 14. How can you write an RAII wrapper for a C resource?

**Short answer:** Store the C resource handle in a class and release it in the destructor.

**Detailed answer:**
RAII is especially useful at C API boundaries because C APIs often use manual acquire/release pairs such as `fopen/fclose`, `malloc/free`, or `pthread_mutex_init/pthread_mutex_destroy`. A C++ wrapper can make ownership explicit and exception-safe.

**Example:**

```cpp
#include <cstdio>
#include <stdexcept>

class File {
public:
    explicit File(const char* path)
        : file_(std::fopen(path, "r")) {
        if (!file_) {
            throw std::runtime_error("failed to open file");
        }
    }

    ~File() {
        std::fclose(file_);
    }

    File(const File&) = delete;
    File& operator=(const File&) = delete;

private:
    std::FILE* file_;
};
```

The wrapper prevents leaks if later code throws, and deleting copy operations prevents two objects from closing the same handle.

**Interview point:** A good RAII wrapper must define ownership semantics, not just call cleanup in a destructor.

**Common mistake:** Allowing the compiler-generated copy constructor for a unique resource handle.

## 15. What is the difference between automatic, dynamic, and static object destruction?

**Short answer:** Automatic objects are destroyed at scope exit, dynamic objects are destroyed by `delete` or an owning object, and static objects are destroyed during program shutdown.

**Detailed answer:**
Object destruction depends on storage duration and ownership. Automatic local objects are destroyed in reverse order when their scope ends. Dynamically allocated objects live until explicitly released or managed by an RAII owner such as `std::unique_ptr`. Static storage duration objects are destroyed after `main` exits, but order across translation units can be difficult to reason about.

**Example:**

```cpp
#include <memory>

class Logger {};

Logger globalLogger; // static storage duration

void run() {
    Logger localLogger;                    // automatic storage duration
    auto dynamicLogger = std::make_unique<Logger>(); // dynamic object owned by RAII
}
```

`localLogger` and `dynamicLogger` are cleaned up when `run` returns. `globalLogger` is destroyed during program shutdown.

**Interview point:** Static object destruction order can cause bugs when one global object's destructor uses another global object that has already been destroyed.

**Common mistake:** Thinking dynamic objects are destroyed automatically when a pointer variable goes out of scope. Only the pointer variable is destroyed unless an owning RAII type manages the object.

## 16. What is the static initialization order problem?

**Short answer:** It is the problem that initialization order of non-local static objects across different translation units is not well-defined.

**Detailed answer:**
Within one translation unit, non-local static objects are initialized in declaration order. Across different translation units, the order is generally unspecified. This can cause bugs when one global object depends on another global object that may not have been initialized yet.

**Problem scenario:**

```cpp
// logger.cpp
Logger globalLogger;

// config.cpp
Config globalConfig(globalLogger); // may run before globalLogger is ready
```

A common solution is construct-on-first-use with a function-local static.

```cpp
Logger& logger() {
    static Logger instance;
    return instance;
}
```

Since C++11, initialization of function-local static variables is thread-safe.

**Interview point:** Prefer avoiding complex global initialization. If global state is necessary, function-local statics can make initialization lazy and ordered by first use.

**Common mistake:** Assuming globals across source files initialize in link order or include order.

## 17. What is the difference between `= default` and `{}` for special member functions?

**Short answer:** `= default` asks the compiler to generate the normal special member behavior. `{}` provides a user-defined empty function body.

**Detailed answer:**
Defaulting a special member function preserves compiler-generated semantics when those semantics are correct. Writing an empty body can change type traits and behavior, such as triviality, implicit move generation, or exception specification.

**Example:**

```cpp
class A {
public:
    ~A() = default;
};

class B {
public:
    ~B() {}
};
```

Both destructors do no visible work, but `A` may remain trivially destructible when possible, while `B` has a user-provided destructor.

**Interview point:** Use `= default` when the compiler-generated operation is exactly what you want. It communicates intent and preserves useful properties.

**Common mistake:** Writing empty constructors or destructors out of habit, accidentally changing special member generation or type traits.

## 18. What is inheriting constructors?

**Short answer:** Inheriting constructors lets a derived class expose selected base-class constructors with a `using` declaration.

**Detailed answer:**
If a derived class does not need custom construction logic, it can inherit constructors from its base. This avoids repetitive forwarding constructors, but it does not remove the need to think about derived members and invariants.

**Example:**

```cpp
class BaseConfig {
public:
    explicit BaseConfig(int port);
    BaseConfig(std::string host, int port);
};

class ServerConfig : public BaseConfig {
public:
    using BaseConfig::BaseConfig;
};
```

Now `ServerConfig` can be constructed using the inherited `BaseConfig` constructor signatures.

**Interview point:** Inherited constructors initialize the base part. Any added derived members are initialized normally, so adding members with invariants may require explicit constructors.

**Common mistake:** Assuming inheriting constructors copies all construction behavior safely even after the derived class gains new state.

## 19. What is two-phase initialization, and why is it risky?

**Short answer:** Two-phase initialization creates an object first and then requires a separate initialization call before the object is usable.

**Detailed answer:**
Two-phase initialization is common in C APIs but risky in C++ because it allows partially initialized objects to exist. Callers may forget to call `init`, call methods too early, or fail to clean up correctly if initialization fails.

**Risky example:**

```cpp
class Socket {
public:
    bool init(const char* address);
    void send(const char* message);
};

Socket socket;
socket.send("hello"); // object may not be initialized
```

Prefer acquiring resources in constructors or factory functions that return either a valid object or an error.

```cpp
class Socket {
public:
    static std::expected<Socket, Error> connect(std::string_view address);
    void send(std::string_view message);

private:
    explicit Socket(int fd) : fd_(fd) {}
    int fd_;
};
```

**Interview point:** Good C++ object design avoids invalid intermediate states when possible.

**Common mistake:** Using default construction plus `init()` because it feels simpler, then spreading validity checks across every member function.

## 20. What does exception safety mean for constructors and destructors?

**Short answer:** Constructors should either complete successfully with a valid object or throw after cleaning up constructed subobjects; destructors should release resources without throwing.

**Detailed answer:**
A constructor establishes class invariants. If it cannot do so, throwing is often the right choice. RAII members ensure partially constructed objects clean up correctly. A destructor runs during normal scope exit and stack unwinding, so throwing from a destructor can cause `std::terminate` if another exception is already active.

**Example:**

```cpp
class Transaction {
public:
    Transaction() : lock_(mutex_) {
        openLog();
    }

    ~Transaction() noexcept {
        closeLogNoThrow();
    }

private:
    std::lock_guard<std::mutex> lock_;
};
```

**Interview point:** Constructors may throw; destructors should usually be `noexcept` and handle cleanup failures internally or expose explicit close/commit operations for errors that callers must observe.

**Common mistake:** Returning an error code from a constructor is impossible, so designs that need fallible construction should use exceptions or factory functions.

## 21. Why does member declaration order matter during construction?

**Short answer:** Data members are initialized in the order they are declared in the class, not in the order listed in the constructor initializer list.

**Detailed answer:**
C++ uses declaration order for member initialization and the reverse order for member destruction. The initializer list order does not control the real initialization order. This matters when one member depends on another.

**Example:**

```cpp
#include <string>

class User {
public:
    User(std::string name)
        : displayName_(name_), name_(std::move(name)) {}

private:
    std::string name_;
    std::string displayName_;
};
```

Even though `displayName_` appears first in the initializer list, `name_` is initialized first because it is declared first. Many compilers warn when initializer list order differs from declaration order.

**Better style:**

```cpp
class User {
public:
    User(std::string name)
        : name_(std::move(name)), displayName_(name_) {}

private:
    std::string name_;
    std::string displayName_;
};
```

**Interview point:** Constructor initializer lists should usually follow member declaration order to avoid misleading readers and hiding dependency bugs.

**Common mistake:** Reordering initializer list entries and expecting that to change initialization order.

## 22. What are common pitfalls with delegating constructors?

**Short answer:** Delegating constructors reduce duplication, but they can hide invalid defaults, make overload behavior confusing, or create construction cycles if misused.

**Detailed answer:**
A delegating constructor calls another constructor of the same class. It is useful when multiple constructors should share one initialization path. However, once a constructor delegates, it cannot also directly initialize members in its own initializer list.

**Example:**

```cpp
#include <string>

class Server {
public:
    Server() : Server("localhost", 8080) {}

    Server(std::string host, int port)
        : host_(std::move(host)), port_(port) {}

private:
    std::string host_;
    int port_;
};
```

**Pitfall:**

```cpp
class Bad {
public:
    Bad() : Bad(0) {}
    Bad(int) : Bad() {} // construction cycle, ill-formed
};
```

**Interview point:** Delegating constructors are best when there is one primary constructor that establishes invariants, and other constructors clearly forward to it.

**Common mistake:** Using delegating constructors to paper over unclear object states instead of defining one strong invariant-establishing path.

## 23. How should RAII types handle move construction and move assignment?

**Short answer:** Move operations for RAII types should transfer resource ownership and leave the moved-from object safe to destroy.

**Detailed answer:**
A RAII object owns a resource and releases it in its destructor. If it supports moving, the move operation must ensure exactly one object owns the resource after the move. The moved-from object should be placed in an empty state that its destructor can safely handle.

**Example:**

```cpp
#include <utility>

class FileDescriptor {
public:
    explicit FileDescriptor(int fd) : fd_(fd) {}

    ~FileDescriptor() {
        if (fd_ != -1) {
            close(fd_);
        }
    }

    FileDescriptor(const FileDescriptor&) = delete;
    FileDescriptor& operator=(const FileDescriptor&) = delete;

    FileDescriptor(FileDescriptor&& other) noexcept
        : fd_(std::exchange(other.fd_, -1)) {}

    FileDescriptor& operator=(FileDescriptor&& other) noexcept {
        if (this != &other) {
            if (fd_ != -1) {
                close(fd_);
            }
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

private:
    int fd_ = -1;
};
```

**Interview point:** Move-enabled RAII requires a clear empty state and usually `noexcept` move operations so containers can move objects efficiently.

**Common mistake:** Copying the raw handle during move construction, causing both objects to release the same resource.

## 24. When should a RAII class provide an explicit `close`, `commit`, or `release` function?

**Short answer:** Provide explicit cleanup functions when callers must observe cleanup errors, control timing, or intentionally transfer ownership out of the RAII object.

**Detailed answer:**
Destructors are good for guaranteed cleanup, but they are not good places to report important failures. If closing a file, committing a transaction, or flushing data can fail in a way callers must handle, expose an explicit operation that returns an error or throws before destruction.

**Example:**

```cpp
class Transaction {
public:
    void commit();   // reports failure to caller
    void rollback() noexcept;

    ~Transaction() noexcept {
        if (!committed_) {
            rollback();
        }
    }

private:
    bool committed_ = false;
};
```

For ownership transfer, a `release` function can deliberately stop the RAII object from owning the resource.

```cpp
int release() noexcept {
    return std::exchange(fd_, -1);
}
```

**Interview point:** RAII destructors guarantee cleanup, while explicit operations let callers handle meaningful outcomes before cleanup becomes implicit.

**Common mistake:** Hiding important cleanup failures inside a destructor where the caller cannot react.

## 25. What is the destruction order of subobjects in C++?

**Short answer:** Destruction happens in the reverse order of construction: derived destructor body, derived members, direct base classes, then virtual base classes.

**Detailed answer:**
When an object is destroyed, C++ follows a strict order. First, the most-derived destructor body runs. Then its data members are destroyed in reverse declaration order. Then direct base-class subobjects are destroyed in reverse construction order. Virtual base classes are destroyed last by the most-derived object.

**Example:**

```cpp
#include <iostream>

struct Member {
    explicit Member(const char* name) : name(name) {}
    ~Member() { std::cout << name << '\n'; }
    const char* name;
};

class Example {
public:
    ~Example() {
        std::cout << "Example destructor body\n";
    }

private:
    Member first_{"first"};
    Member second_{"second"};
};
```

The destructor body runs first, then `second_`, then `first_`.

**Interview point:** Destruction order matters when one member depends on another. Declare members so dependencies outlive the objects that use them.

**Common mistake:** Accessing a member from another member's destructor after that dependency has already been destroyed.

## 26. What is constructor delegation to a private primary constructor?

**Short answer:** It is a pattern where public constructors or factory functions forward to one private constructor that establishes the class invariant.

**Detailed answer:**
When a class has several ways to create a valid object, a single primary constructor can centralize validation and member initialization. This avoids duplicated checks and keeps all construction paths consistent.

**Example:**

```cpp
class Port {
public:
    explicit Port(int value) : Port(value, true) {}

private:
    Port(int value, bool validate) : value_(value) {
        if (validate && (value < 0 || value > 65535)) {
            throw std::out_of_range("port");
        }
    }

    int value_;
};
```

**Interview point:** Multiple constructors should not mean multiple inconsistent invariant paths.

**Common mistake:** Copying validation logic into every constructor and later updating only one path.

## 27. What is a factory function, and when is it better than a constructor?

**Short answer:** A factory function creates objects through a named function and is useful when construction needs validation, error reporting, caching, or choosing derived types.

**Detailed answer:**
Constructors cannot return error codes and cannot choose a different concrete return type. A factory can return `std::optional`, `std::expected`, `std::unique_ptr<Base>`, or another result type.

**Example:**

```cpp
class Socket {
public:
    static std::expected<Socket, Error> connect(std::string_view address);

private:
    explicit Socket(int fd) : fd_(fd) {}
    int fd_;
};
```

**Interview point:** Constructors are good for directly establishing a valid object. Factories are better when creation is a process with alternatives or recoverable failure.

**Common mistake:** Using two-phase initialization instead of a factory that returns either a valid object or an error.

## 28. What happens when a constructor throws?

**Short answer:** The object is not considered constructed, fully constructed members are destroyed, and the class destructor itself does not run.

**Detailed answer:**
If construction fails, C++ destroys already-constructed base classes and members in reverse order. The destructor for the most-derived object does not run because that object never fully existed.

**Example:**

```cpp
class ResourceOwner {
public:
    ResourceOwner() : first_(), second_() {
        mayThrow();
    }

private:
    Resource first_;
    Resource second_;
};
```

If `mayThrow()` throws, `second_` and `first_` are destroyed automatically.

**Interview point:** Put resources in RAII members so partial construction cleans up correctly.

**Common mistake:** Acquiring raw resources in a constructor body before a possible throw and not wrapping them immediately.

## 29. What is function-try-block syntax for constructors?

**Short answer:** A function-try-block catches exceptions from member and base initialization as well as the constructor body.

**Detailed answer:**
Constructor member initialization happens before the constructor body. A normal `try` inside the body cannot catch failures from member initializers. A function-try-block can observe them, usually to add context, then the exception is rethrown automatically if not otherwise handled correctly.

**Example:**

```cpp
class Service {
public:
    Service() try : connection_(openConnection()) {
    } catch (const std::exception& ex) {
        throw ServiceError(ex.what());
    }

private:
    Connection connection_;
};
```

**Interview point:** Function-try-blocks are rare but useful when constructor initialization needs exception translation.

**Common mistake:** Expecting a `try` block inside the constructor body to catch member initializer failures.

---

## 30. What is the Rule of Zero in RAII design?

**Short answer:** The Rule of Zero says classes should avoid declaring special member functions when their members already manage resources correctly.

**Detailed answer:**
If a class stores resources in RAII types such as `std::string`, `std::vector`, `std::unique_ptr`, or custom handle wrappers, the compiler-generated destructor, copy, and move operations may be exactly right.

**Example:**

```cpp
class UserProfile {
private:
    std::string name_;
    std::vector<std::string> roles_;
};
```

No destructor or copy constructor is needed.

**Interview point:** The best resource-management code is often code you do not write because member types already encode ownership.

**Common mistake:** Adding empty destructors or manual copy operations to classes whose members already do the right thing.

---

## 31. What is a noexcept destructor, and why is it important?

**Short answer:** A `noexcept` destructor promises not to let exceptions escape, which is important during stack unwinding and container cleanup.

**Detailed answer:**
Destructors are implicitly `noexcept` in many cases. If a destructor throws while another exception is already being handled, the program calls `std::terminate`. Cleanup code should handle failures internally or expose explicit operations such as `close()` or `commit()` before destruction.

**Example:**

```cpp
class File {
public:
    ~File() noexcept {
        closeNoThrow();
    }
};
```

**Interview point:** Destructors should release resources reliably without becoming an error-reporting channel.

**Common mistake:** Throwing from a destructor to report cleanup failure.

---

## 32. What is RAII for locks?

**Short answer:** RAII lock wrappers acquire a mutex in their constructor and release it in their destructor.

**Detailed answer:**
RAII prevents forgetting to unlock a mutex when a function returns early or throws. Standard wrappers include `std::lock_guard`, `std::unique_lock`, and `std::scoped_lock`.

**Example:**

```cpp
std::mutex mutex;
std::vector<int> values;

void add(int value) {
    std::lock_guard<std::mutex> lock(mutex);
    values.push_back(value);
}
```

**Interview point:** Lock lifetime should be scoped as tightly as possible and visible in code.

**Common mistake:** Manually calling `lock()` and `unlock()` across code paths that can return or throw.

---

## 33. What is `std::scoped_lock`?

**Short answer:** `std::scoped_lock` is an RAII lock wrapper that can lock one or more mutexes and unlock them at scope exit.

**Detailed answer:**
When locking multiple mutexes, `std::scoped_lock` uses deadlock-avoidance logic equivalent to `std::lock`. This is safer than manually locking mutexes in inconsistent order.

**Example:**

```cpp
void transfer(Account& from, Account& to, int amount) {
    std::scoped_lock lock(from.mutex, to.mutex);
    from.balance -= amount;
    to.balance += amount;
}
```

**Interview point:** Multi-mutex locking needs a consistent strategy; RAII handles release, but lock acquisition order still matters.

**Common mistake:** Locking two mutexes manually in different orders in different functions.

---

## 34. What is ownership release in RAII?

**Short answer:** Ownership release intentionally stops a RAII object from managing a resource, usually transferring responsibility to someone else.

**Detailed answer:**
`release()` is different from cleanup. It returns the raw resource and leaves the RAII object empty. The caller must then ensure the resource is eventually closed or deleted.

**Example:**

```cpp
std::unique_ptr<int> value = std::make_unique<int>(42);
int* raw = value.release(); // caller now owns raw
 delete raw;
```

**Interview point:** `release()` should be rare and usually appears at ownership-transfer boundaries.

**Common mistake:** Calling `release()` when `reset()` or normal destruction was intended, causing a leak.

---

## 35. What is the difference between `reset` and `release` in RAII wrappers?

**Short answer:** `reset` destroys or replaces the owned resource; `release` gives up ownership without destroying the resource.

**Detailed answer:**
For `std::unique_ptr`, `reset()` deletes the current object and optionally takes ownership of a new pointer. `release()` returns the pointer and sets the smart pointer to null without deletion.

**Example:**

```cpp
auto p = std::make_unique<int>(1);
p.reset(new int(2)); // deletes old int

int* raw = p.release(); // does not delete
 delete raw;
```

**Interview point:** Use `reset` for cleanup/replacement and `release` only for explicit ownership transfer.

**Common mistake:** Using `release` to "free" memory.

---

## 36. What is a moved-from RAII object allowed to do?

**Short answer:** A moved-from RAII object must be safe to destroy and assign to, but it usually has no useful resource.

**Detailed answer:**
Move operations transfer ownership. The source object should be left in a valid empty state, such as a null pointer or invalid file descriptor. Member functions should either handle that empty state or document preconditions.

**Example:**

```cpp
FileHandle a(openFile());
FileHandle b(std::move(a));
// a is valid but no longer owns the file
```

**Interview point:** Moved-from does not mean destroyed. Destructors and assignment must still work.

**Common mistake:** Leaving a moved-from object with the old raw handle, causing double cleanup.

---

## 37. What is RAII for temporary state changes?

**Short answer:** RAII can restore temporary state automatically when a scope exits.

**Detailed answer:**
RAII is not only for memory and handles. It can manage any acquire/release or set/restore pair, such as changing a flag, current directory, locale, logging level, or test environment state.

**Example:**

```cpp
class FlagGuard {
public:
    FlagGuard(bool& flag, bool value) : flag_(flag), old_(flag) {
        flag_ = value;
    }
    ~FlagGuard() { flag_ = old_; }
private:
    bool& flag_;
    bool old_;
};
```

**Interview point:** RAII expresses scoped responsibility, not just heap ownership.

**Common mistake:** Manually restoring state at the end of a function and missing early returns or exceptions.

---

## 38. What is a destructor side effect, and why should it be designed carefully?

**Short answer:** A destructor side effect is work done during destruction beyond local cleanup, such as logging, flushing, committing, or notifying.

**Detailed answer:**
Destructor side effects can be useful but surprising because destruction may happen during exception unwinding, container reallocation, or scope exit that callers do not think about. Important operations that can fail should usually be explicit.

**Example:**

```cpp
class AuditEvent {
public:
    ~AuditEvent() noexcept { writeBestEffortLog(); }
};
```

**Interview point:** Destructors are best for guaranteed cleanup, not for complex business actions that callers must observe.

**Common mistake:** Committing a transaction in a destructor without giving callers a clear way to handle commit failure.

---

## 39. What is initialization dependency between members?

**Short answer:** It is when one data member's initialization depends on another member already being initialized.

**Detailed answer:**
Because members initialize in declaration order, dependency order should be represented by member declaration order. If member `b_` depends on `a_`, declare `a_` first and list initializers in the same order.

**Example:**

```cpp
class Parser {
public:
    Parser(std::string text) : text_(std::move(text)), view_(text_) {}
private:
    std::string text_;
    std::string_view view_;
};
```

**Interview point:** Initialization dependencies are a design smell if they are subtle; make them obvious or avoid storing dependent views.

**Common mistake:** Declaring `view_` before `text_` and assuming initializer-list order fixes it.

---

## 40. How do RAII and exception safety work together?

**Short answer:** RAII makes exception safety practical by ensuring resources are released automatically when exceptions exit a scope.

**Detailed answer:**
Exception-safe code defines what remains true if an operation fails. RAII handles cleanup so code can focus on invariants and rollback. Strong exception safety often uses temporary objects, swaps, or commit/rollback designs.

**Example:**

```cpp
void update(Config& config, Config next) {
    validate(next);
    config = std::move(next); // commit after validation succeeds
}
```

If validation throws, the original config is unchanged.

**Interview point:** RAII is the foundation of idiomatic C++ exception safety.

**Common mistake:** Disabling exceptions or avoiding RAII and then manually duplicating cleanup logic everywhere.

---

## 41. What is a scope guard?

**Short answer:** A scope guard is an RAII object that runs a cleanup action when the current scope exits.

**Detailed answer:**
Scope guards are useful when cleanup is not naturally represented by an existing resource wrapper. They can restore state, roll back partial changes, release temporary registrations, or run a callback on every exit path.

**Example:**

```cpp
class ScopeExit {
public:
    explicit ScopeExit(std::function<void()> action) : action_(std::move(action)) {}
    ~ScopeExit() { action_(); }

private:
    std::function<void()> action_;
};
```

Production implementations usually handle move-only actions, cancellation, and `noexcept` behavior carefully.

**Interview point:** Scope guards generalize RAII to arbitrary scoped cleanup.

**Common mistake:** Using scope guards for complex business logic instead of simple cleanup or rollback.

---

## 42. What is a commit-or-rollback RAII pattern?

**Short answer:** It is a pattern where destruction rolls back unless the operation has been explicitly committed.

**Detailed answer:**
This pattern is useful for transactions, temporary file updates, locks with state changes, and multi-step operations. The object starts in a rollback-needed state. If all steps succeed, the caller calls `commit()`. If an exception or early return happens first, the destructor rolls back.

**Example:**

```cpp
class TransactionGuard {
public:
    ~TransactionGuard() noexcept {
        if (!committed_) {
            rollbackNoThrow();
        }
    }

    void commit() {
        commitChanges();
        committed_ = true;
    }

private:
    bool committed_ = false;
};
```

**Interview point:** RAII can encode failure-path behavior, not just final cleanup.

**Common mistake:** Committing in the destructor and losing the ability to report commit failure.

---

## 43. How should RAII wrappers handle cleanup failure?

**Short answer:** Destructors should not throw; cleanup failures should be handled internally or exposed through explicit operations before destruction.

**Detailed answer:**
Some cleanup operations can fail, such as flushing a file, committing a transaction, or closing a network connection. A destructor is usually the wrong place to report such failures because it may run during stack unwinding and cannot force callers to handle errors.

**Example design:**

```cpp
class OutputFile {
public:
    void close();       // may report failure
    ~OutputFile() noexcept {
        closeNoThrow();
    }
};
```

Callers that care about errors call `close()` explicitly. The destructor remains best-effort cleanup.

**Interview point:** Separate guaranteed cleanup from error-reporting operations.

**Common mistake:** Throwing from destructors to report a failed `close` or `flush`.

---

## 44. What is the difference between owning and observing RAII wrappers?

**Short answer:** Owning wrappers release a resource in their destructor; observing wrappers only refer to a resource owned elsewhere.

**Detailed answer:**
An owning RAII wrapper represents responsibility for cleanup. An observing wrapper may provide convenient access, but it must not release the resource. Mixing the two roles can cause double cleanup or dangling references.

**Example:**

```cpp
class FileOwner {
public:
    ~FileOwner() { close(fd_); }
private:
    int fd_ = -1;
};

class FileView {
public:
    explicit FileView(int fd) : fd_(fd) {}
private:
    int fd_; // non-owning
};
```

**Interview point:** RAII is about ownership; not every wrapper around a handle should own it.

**Common mistake:** Closing a borrowed file descriptor or handle in a non-owning helper object.

---

## 45. What is RAII for registration and deregistration?

**Short answer:** RAII can ensure that a registration is automatically undone when the registration object is destroyed.

**Detailed answer:**
Programs often register callbacks, observers, metrics, signal handlers, or temporary hooks. Forgetting to unregister can cause callbacks to fire on destroyed objects or leave global state polluted.

**Example:**

```cpp
class Subscription {
public:
    Subscription(EventBus& bus, Token token) : bus_(bus), token_(token) {}
    ~Subscription() { bus_.unsubscribe(token_); }

private:
    EventBus& bus_;
    Token token_;
};
```

The subscription object owns the registration lifetime.

**Interview point:** RAII works well for paired operations such as register/unregister.

**Common mistake:** Registering callbacks with raw `this` pointers and forgetting to unregister before destruction.

## 46. What is constructor validation?

**Short answer:** Constructor validation checks inputs before allowing an object to exist in an invalid state.

**Detailed answer:**
A constructor should establish class invariants. If inputs are invalid and no meaningful object can be created, the constructor can throw, or a factory can return an error type such as `std::expected`.

**Example:**

```cpp
class Percentage {
public:
    explicit Percentage(int value) : value_(value) {
        if (value < 0 || value > 100) {
            throw std::out_of_range("percentage");
        }
    }

private:
    int value_;
};
```

**Interview point:** A constructed object should be ready to use and should satisfy its invariants.

**Common mistake:** Creating invalid objects and requiring every member function to check whether initialization really succeeded.

## 47. What is a named constructor idiom?

**Short answer:** The named constructor idiom uses static factory functions with descriptive names instead of relying only on overloaded constructors.

**Detailed answer:**
Constructors all have the class name, so overloads can be ambiguous when several construction meanings use similar parameter types. Named factories make intent explicit and can validate or return error-aware results.

**Example:**

```cpp
class Duration {
public:
    static Duration fromSeconds(int seconds) { return Duration(seconds); }
    static Duration fromMinutes(int minutes) { return Duration(minutes * 60); }

private:
    explicit Duration(int seconds) : seconds_(seconds) {}
    int seconds_;
};
```

**Interview point:** Named construction improves readability when parameter meaning matters.

**Common mistake:** Using several `int` constructors and forcing callers to remember units or ordering.

## 48. What is RAII for temporary files?

**Short answer:** RAII can ensure temporary files are removed unless ownership is intentionally transferred or committed.

**Detailed answer:**
Temporary files are common in atomic updates, tests, and intermediate processing. An RAII wrapper can create the file and delete it on destruction if the operation fails. If the file is successfully renamed or committed, the wrapper can disable cleanup.

**Conceptual example:**

```cpp
class TemporaryFile {
public:
    ~TemporaryFile() noexcept {
        if (active_) {
            removeNoThrow(path_);
        }
    }

    void commit() { active_ = false; }

private:
    std::filesystem::path path_;
    bool active_ = true;
};
```

**Interview point:** RAII is useful for filesystem state, not only in-memory resources.

**Common mistake:** Leaving temporary files behind on exceptions or early returns.

---

## 49. What is the difference between deterministic destruction and garbage collection?

**Short answer:** Deterministic destruction runs cleanup at a known scope or lifetime end; garbage collection reclaims memory at a runtime-chosen time.

**Detailed answer:**
C++ destructors run when objects with automatic storage leave scope, when owning objects are destroyed, or when delete-like ownership releases happen. This makes RAII effective for locks, files, sockets, and other non-memory resources. Garbage-collected systems may reclaim memory later, so finalization is not usually a reliable resource-release mechanism.

**Example:**

```cpp
{
    std::lock_guard<std::mutex> lock(mutex);
    updateSharedState();
} // mutex unlocked here
```

**Interview point:** RAII depends on predictable destruction timing.

**Common mistake:** Thinking RAII is only about memory rather than deterministic release of all resources.

## 50. How do you design a robust RAII wrapper for a C handle?

**Short answer:** Store the handle, define ownership clearly, release it in a `noexcept` destructor, support move semantics, and disable copying unless duplication is meaningful.

**Detailed answer:**
A C handle wrapper should represent exactly one owner. It should initialize to an invalid handle, clean up only valid handles, transfer ownership on move, and avoid double release. If the C API supports duplicating handles, copying can be implemented deliberately; otherwise it should be deleted.

**Checklist:**

- What value represents an invalid handle?
- Which function releases the handle?
- Can release fail, and how is that reported?
- Is copying meaningful or dangerous?
- Is moving `noexcept`?
- Does the wrapper expose a non-owning view when needed?

**Example skeleton:**

```cpp
class Handle {
public:
    explicit Handle(int fd) : fd_(fd) {}
    ~Handle() noexcept { closeIfValid(); }

    Handle(const Handle&) = delete;
    Handle& operator=(const Handle&) = delete;
    Handle(Handle&& other) noexcept : fd_(std::exchange(other.fd_, -1)) {}

private:
    int fd_ = -1;
};
```

**Interview point:** A good RAII wrapper makes the invalid states and ownership transfers explicit.

**Common mistake:** Writing a destructor but forgetting to define or delete copy operations, causing double cleanup.
